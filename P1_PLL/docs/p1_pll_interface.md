# P1 — PLL interface contract

This is the interface P1 offers to the rest of the project. It is written
against what already exists in the repository, so every signal is labelled
**confirmed** or **proposed**.

- **Confirmed** means the signal is already driven or sampled by committed RTL
  (today that means `P3_DVFS_Controller/rtl/p3_dvfs_controller.v`). P1 must
  match it.
- **Proposed** means P1 is introducing it in this session. Nothing else in the
  repository refers to it yet, so it can still be renamed or dropped.

No frequency values appear anywhere in this document. P1 handles *frequency
codes*, not megahertz. The code-to-frequency mapping is a Cadence calibration
input and is deliberately out of scope until the behavioral clock model exists.

Related existing documents:
[`../../P3_DVFS_Controller/docs/interface_assumptions.md`](../../P3_DVFS_Controller/docs/interface_assumptions.md)
sections 1, 3, 4 and 5 state what P3 assumes of P1. This contract answers
sections 3 and 4 and leaves section 5 open — see section 9 below.

---

## 1. What already exists

P3 is the only sub-block with committed RTL. It drives P1 through three ports:

| P3 port | Direction (P3 view) | Width |
|---------|---------------------|-------|
| `pll_req` | output | 1 |
| `pll_freq_sel` | output | 2 |
| `pll_done` | input | 1 |

There is no P2, P4 or PMU RTL, and **no P4 or PMU specification of any kind** in
the repository. P4's interface is described only from P3's side, in P3's own
assumptions document. So nothing outside P3 constrains P1 today.

## 2. Port list

```verilog
module p1_pll_controller #(
    parameter integer RECONFIG_CYCLES = 4,
    parameter integer LOCK_TIMEOUT    = 1024
)(
    input  wire       clk_ref,
    input  wire       rst_n,

    input  wire       freq_req,
    input  wire [1:0] freq_sel,
    input  wire       err_clear,

    output reg        freq_ack,
    output reg        pll_done,
    output reg        pll_busy,
    output reg        pll_error,

    output reg        pll_locked,
    output reg [1:0]  current_freq_sel,
    output reg        clock_valid,

    output reg        pll_reconfig_en,
    output reg [1:0]  pll_freq_code,
    input  wire       pll_lock_in
);
```

### Inputs

| Signal | Width | Source | Status | Description |
|--------|-------|--------|--------|-------------|
| `clk_ref` | 1 | system | **proposed** | Reference / control clock. All P1 control state updates on `posedge clk_ref`. P3 calls the same net `clk`. |
| `rst_n` | 1 | system | **confirmed** | Asynchronous active-low reset, same convention as P3. |
| `freq_req` | 1 | P3 | **confirmed as `pll_req`** | Level-sensitive frequency change request. |
| `freq_sel` | 2 | P3 | **confirmed as `pll_freq_sel`** | Target frequency code. |
| `err_clear` | 1 | PMU / software | **proposed** | One-cycle pulse that clears the sticky `pll_error`. No block drives it yet. |
| `pll_lock_in` | 1 | PLL model | **proposed** | Raw lock indication from the behavioral PLL. Treated as asynchronous. |

### Outputs

| Signal | Width | Destination | Status | Description |
|--------|-------|-------------|--------|-------------|
| `freq_ack` | 1 | P3 / PMU | **proposed** | Single-cycle completion pulse. Exactly one per accepted request. |
| `pll_done` | 1 | P3 | **confirmed** | Level acknowledgement. Low while P1 works, high from completion until `freq_req` is released. This is the pin P3 samples today. |
| `pll_busy` | 1 | P3 / PMU | **proposed** | High while a request is in progress. |
| `pll_error` | 1 | PMU / software | **proposed** | Sticky error flag. |
| `pll_locked` | 1 | status | **proposed** | Synchronised view of `pll_lock_in`. |
| `current_freq_sel` | 2 | status | **proposed** | Last successfully established frequency code. |
| `clock_valid` | 1 | status / clock gating | **proposed** | High when `gpu_clk` is locked and usable at `current_freq_sel`. |
| `pll_reconfig_en` | 1 | PLL model | **proposed** | Level strobe telling the PLL to retune. |
| `pll_freq_code` | 2 | PLL model | **proposed** | Code handed to the PLL. Held stable after reconfiguration. |

`gpu_clk` is **not** a port of this module. It is generated by the behavioral
clock model added in Session 2, which wraps this controller. See section 8.

## 3. Name mapping for integration

P1's ports are named from inside the PLL block, where `pll_req` would describe
an input rather than a request P1 makes. Integration is a direct wiring:

| P3 net | P1 port | Note |
|--------|---------|------|
| `clk` | `clk_ref` | must be the same net |
| `rst_n` | `rst_n` | |
| `pll_req` | `freq_req` | |
| `pll_freq_sel` | `freq_sel` | |
| `pll_done` | `pll_done` | P3 samples the level, not the pulse |

`freq_ack`, `pll_busy`, `pll_error`, `pll_locked`, `current_freq_sel` and
`clock_valid` have no consumer in P3. They are left unconnected until a PMU
exists.

**If the team prefers P3's names on P1's ports as well**, rename `freq_req` to
`pll_req` and `freq_sel` to `pll_freq_sel`. Nothing in the FSM depends on the
choice. See the open question in section 9.

## 4. Frequency code encoding

Confirmed: the same two-bit encoding is shared by the whole project, stated in
the root [`README.md`](../../README.md) and used by all three P3 modules.

| Code | Level |
|------|-------|
| `2'b00` | LOW |
| `2'b01` | MEDIUM |
| `2'b10` | HIGH |
| `2'b11` | Reserved / invalid |

P1 treats `2'b11` as an invalid request and rejects it — section 6. P3 already
filters `2'b11` and never issues it, so this path is defensive only.

P1 attaches **no frequency value** to any code. It only guarantees that a
request for a code results in the PLL being reconfigured to that code and
locked, or in an error.

---

## 5. Request / acknowledgement handshake

Deterministic, level-sensitive, return-to-zero. Every step is on `clk_ref`.

1. The requester drives `freq_sel` and raises `freq_req`. `freq_sel` must be
   stable for as long as `freq_req` is high.
2. P1 samples the request only in `IDLE`. On the first `posedge clk_ref` with
   `freq_req` high, P1 latches `freq_sel` internally and raises `pll_busy`.
   Changes to `freq_sel` after this point are ignored.
3. `pll_done` is guaranteed low for **at least two `clk_ref` cycles** after
   `freq_req` rises, whatever the request. This is what makes P3's
   `pll_seen_busy` qualification safe.
4. P1 reconfigures the PLL and waits for lock.
5. On success P1 pulses `freq_ack` for exactly one cycle, raises `pll_done`,
   drops `pll_busy`, and updates `current_freq_sel` and `clock_valid`.
6. `pll_done` stays high until the requester releases `freq_req`. P1 then
   returns to `IDLE`.
7. P1 accepts no new request until `freq_req` has been seen low. Because step 6
   is the only way out of the completion state, this is structural rather than a
   separate check.

### Why there are two acknowledgement signals

`pll_done` is the level handshake P3's existing RTL needs. `freq_ack` is a
single-cycle pulse for an event-driven consumer such as a future PMU. Both are
decoded from the same completion state, so they can never disagree, and
`freq_ack` fires exactly once per accepted request.

### Requests arriving while busy

Ignored. `freq_req` and `freq_sel` are sampled only in `IDLE`, so a request
raised mid-transition has no effect until the in-flight transition finishes and
`freq_req` has returned low. This matches P3's own behaviour of finishing an
in-flight change before looking at a new request.

## 6. Supported-state validation

| `freq_sel` | P1 behaviour |
|------------|--------------|
| `2'b00`, `2'b01`, `2'b10` | accepted |
| `2'b11` | rejected: P1 enters the error state, sets sticky `pll_error`, issues **no** `freq_ack` and **no** `pll_done` |

A rejected request does not touch the PLL. `pll_reconfig_en` is never asserted,
`current_freq_sel` is unchanged and `clock_valid` is unaffected, so a running
GPU clock survives an invalid request intact.

---

## 7. Same-state requests

A request whose `freq_sel` already equals `current_freq_sel`, with
`clock_valid` high, is acknowledged **without reconfiguring the PLL**:

- `pll_reconfig_en` is never asserted and `pll_freq_code` does not change.
- `clock_valid` stays high throughout; the GPU clock is never interrupted.
- `freq_ack` pulses once and `pll_done` behaves exactly as for a real change.

If `clock_valid` is low the request is treated as a real change even when the
code matches, because the PLL is not known to be running at that code.

---

## 8. Clocking, reset and domain crossing

1. All P1 control state is clocked by `clk_ref`. **No control logic is clocked
   by `gpu_clk`.** That is deliberate: the generated clock stops or glitches
   during reconfiguration, so an FSM on it could not sequence its own recovery.
2. `rst_n` is asynchronous and active-low, matching P3.
3. `pll_lock_in` is treated as asynchronous and passes through a two-flop
   synchroniser before any FSM decision uses it. `pll_locked` is the
   synchronised value.
4. `pll_done`, `freq_ack`, `pll_busy` and all status outputs are generated on
   `clk_ref`. **So P3 needs no synchroniser on `pll_done`, provided P3's `clk`
   and P1's `clk_ref` are the same net.** This answers open item 4 in P3's
   assumptions document for the P1 side.
5. Reset behaviour from any state: P1 returns to `IDLE`,
   `current_freq_sel = 2'b00`, `pll_freq_code = 2'b00`, `clock_valid = 0`,
   `pll_error = 0`, and `freq_ack`, `pll_done` and `pll_busy` all low. Any
   in-flight request is abandoned with no acknowledgement. The requester must
   re-issue it.
6. After reset P1 adopts the reset code (`2'b00`, LOW) once the PLL reports
   lock, and raises `clock_valid` with `current_freq_sel = 2'b00`. **No
   `freq_ack` is issued for this bring-up**, because no request was made. The
   Session 2 clock model must therefore come up at the LOW code.

## 9. Error handling

| Condition | P1 response |
|-----------|-------------|
| Invalid `freq_sel` | error state, sticky `pll_error`, no acknowledgement, PLL untouched |
| Lock not reached within `LOCK_TIMEOUT` cycles | error state, sticky `pll_error`, no acknowledgement, `clock_valid` stays low, `current_freq_sel` not updated |
| Lock lost while `clock_valid` was high | `clock_valid` drops, sticky `pll_error` set, P1 re-waits for lock with the timeout armed, and restores `clock_valid` on relock. **No `freq_ack`** — nothing was requested |
| `LOCK_TIMEOUT = 0` | timeout disabled, P1 waits indefinitely, matching P3's "unbounded lock time" assumption |

`pll_error` is sticky. It is cleared only by `rst_n` or by a pulse on
`err_clear`. A set in the same cycle as a clear wins.

The error **state** is left as soon as `freq_req` returns low. `err_clear` does
not force the state machine out of it, so an error can never produce an
automatic retry loop.

### Open interface questions

1. **P3 has no error input.** If P1 reaches the error state while P3 holds
   `pll_req` asserted, P3 waits for a `pll_done` that will never come and P1
   waits for a `pll_req` release that will never come. The system deadlocks.
   This is the same gap P3 records as its own open item 5. It needs one of:
   a P3 timeout, a `pll_error` input on P3, or a PMU that owns recovery.
   **Not resolvable inside P1.**
2. **Port naming.** Should P1's request inputs be `freq_req` / `freq_sel`
   (chosen here) or P3's `pll_req` / `pll_freq_sel`?
3. **Is `clk_ref` the same net as P3's `clk`?** Section 8 point 4 depends on it.
   If the two differ, P3 needs a synchroniser on `pll_done` after all.
4. **Who drives `err_clear`?** There is no PMU specification in the repository.
5. **Is a separate loss-of-lock output wanted?** P3's assumptions document asks
   whether loss of lock is signalled on `pll_done` or on a separate pin. P1
   currently reports it on `clock_valid` and `pll_error`, and never on
   `pll_done`.
6. **Reset release.** P3 asks whether `rst_n` is released synchronously with
   respect to the clock. Still unanswered, and it applies to P1 identically.
7. **`RECONFIG_CYCLES` and `LOCK_TIMEOUT` values.** Both are placeholders. They
   are Cadence calibration outputs and cannot be chosen before Session 2.
